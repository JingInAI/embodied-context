# 组件英文使用指导审查记录

本次针对 `v1` 分支审查十个运行组件的输出、英文说明、输入输出规则和历史状态行为，并对照原 `scripts/` 中的说明。修复集中在 `context_components/presentation.py`：补齐如何使用结果推进任务的指导，而不是把字段解释扩写成重复的通用提醒。

## 审查发现与修复

| 组件 | 原说明的主要不足 | 补充的工作方法 | 职责边界 |
| --- | --- | --- | --- |
| `task_context` | 偏重状态名与字段含义，缺少任务模型、下一步检查、失败调整和完成判断。 | 根据任务类型组织工作；无目标时建立临时计划；有目标时核对依赖；按未知、受阻、尝试、支持状态选择指导；新证据到来后局部修订计划；按全部明确要求判断完成。 | 不生成固定动作序列；不把 agent 的决定写回状态；不恢复旧版 `planning_state` 或 `persistence` 协议。 |
| `observation_context` | 提醒区分观测与估计，但缺少选择、对齐和复查证据的过程。 | 选择与当前决策相关的事实，核对来源、场景、视角和时间；检查假设、冲突与撤回；按真实时间依据恢复事件顺序；说明文本接收方如何使用媒体来源。 | 不以引用或读取代替语义理解，不将事件收到顺序视为世界发生顺序。 |
| `spatial_context` | 解释不同几何结果，但缺少比较前的检查及动态数据失效处理。 | 对照 query_id，逐条检查状态、坐标系、单位与物理参考点；在输入或移动坐标系变化后重新计算；区分像素、射线、点和几何距离的使用条件。 | 不固定坐标轴、相机朝向、控制点、物体高度或安全距离，不把端点距离当作完整路径的可行性证明。 |
| `interaction_contract` | 提醒遵守接口，但缺少从意图到参数、组合语义的检查流程。 | 对应操作种类和实体，检查参数、绝对或相对语义、归一化、控制分组及执行规则；自定义操作类型也保留条件式解释。 | 不创建动作接口或执行权限；不假设机器人维度、频率、零值含义或夹爪符号。 |
| `execution_feedback` | 区分提交、接受与执行，但缺少中断后的决策方法。 | 对应请求和实体；核对实际执行与意图差异；结合当前状态和终止记录处理部分效果，避免重复执行；缺少原因时保持未知。 | 不根据执行状态推断任务完成；不以端点变化估计完整轨迹或控制增益。 |
| `response_evidence` | 说明局部统计限制，但缺少何时可使用、更新或拒绝候选估计的过程。 | 检查变量、单位、条件与时效；比较具有可用估计的候选；明确缺失估计不等于零；条件变化后重算。 | 不自动排名、反演动力学或执行补偿，不把预测或合成样本当作真实测量。 |
| `resource_context` | 解释容量和窗口，但缺少具体分配、短缺和过期处理。 | 按资源逐项核对余额、成本和上限；避免重复扣减；存在短缺时调整可选工作；存在不可中断窗口或过期截止时间时追加相应指导。 | 不修改输出长度、实际预留资源、延长期限或虚构成本换算。 |
| `evidence_context` | 说明登记与可读取的区别，但缺少选择来源和定位所需内容的方法。 | 根据当前问题选择来源及 locator，核对身份与范围，使用匹配媒体类型的接口；保留引用，访问失败时报告缺失依赖。 | 只负责资料定位与可读取状态，不承担观测解释或执行结果判定。 |
| `tool_context` | 解释工具注册信息，但缺少选择工具、验证结果、复用历史和失败处理流程。 | 从缺少的信息选择能力，核对输入输出及效果范围；复用前检查输入、版本与范围；只在失败记录出现时追加重试处理指导。 | 不创建可调用接口或重试策略，不连接 backend 或控制机器人；历史调用记录不授予当前能力。 |
| `output_contract` | 说明检查状态，但缺少构造候选、定位错误、保护内容与重新验证的流程。 | 检查完整候选，遵守全部显式规则；精确保留字段出现时追加保护说明；失败后按路径修正并重新检查；候选或约定变化后重新验证。 | 不自动修复或放宽约束，不从格式通过推断答案正确或任务成功。 |

旧版中值得保留的是通用工作方法，而不是特定接口和实验参数。原 `action_stages_context`、相机与动作协议中固定的抓取流程、步数、七维动作和 LIBERO 相机约定没有搬入新版。原代码计算和输出修复说明中的固定调用包装、单次重试规则也没有变成通用组件要求。

## 兼容性与组织

英文说明仍由组件自己的结果驱动，按“工作方法 → 当前状态需要的指导 → 当前字段解释 → 数据”组织，不读取额外文件，不调用模型或工具，不改变组件结果。本次指导改进最初未增加运行参数或 schema 字段；后续任务类型适配增加了可选 task 元数据和 request.task_variants，见下文更新。

任务类型来自显式 `kind`；不会根据任务名字中的 benchmark、机器人或操作词推断类型。执行、推理、混合任务采用不同指导。未知或自定义交互类型使用条件式说明，不要求调用方采用某个控制名称。资料和工具能力始终由调用方显式提供。纯语言接收方不会因为拿到媒体引用就被认为看过媒体。

三个显示形式继续保留：`json` 不增加说明，`text_json` 和 `text` 使用相同的英文指导。完整 JSON 始终用于组件间通信与历史状态；说明不会修改 `content`、证据引用、绑定或 `state_update`。任务说明仅在确实生成状态更新时提及保存边界，且不声称已保存 agent 随后的决定。

## 验证

从组件项目根目录运行：

```bash
PYTHONPATH=. python -B -m unittest discover -s tmp/tests -v
```

在现有 Python 环境中，64 项离线测试全部通过：原有 52 项加上 12 项任务指导回归用例。新用例使用实际组件构建结果，覆盖目标证据撤回、纯推理与混合任务、条件分支、自定义控制类型、部分执行、缺少局部响应支持、资源不足与过期、资料读取、工具历史复用和输出重新验证。

适配器测试扩展到 11 个适配器的全部 54 个声明模式，每种模式检查 3 种显示形式及 2 种接收模态组合，共 324 组交付检查，并检查私有评测字段未泄露、完整 JSON 未被渲染修改。覆盖 LIBERO、LIBERO-plus、LIBERO-Pro、Meta-World、RoboTwin 2.0、RoboCasa365、RoboDojo、RoboCerebra、RoboMME、Isaac Lab Arena、VLABench。原有全部任务目录身份检查也通过。

这验证的是协议与渲染兼容性，不是实际 benchmark、机器人或模型任务表现；本次没有执行这些评测。

## 示例与预算

原工作区的 `../tmp/task_context/` 已重新生成英文任务示例，并同步了中文说明版；中文版仅用于对照，运行时说明仍为英文。两版输入表达相同的合成任务，目标状态仍为 `supported`、`pending`、`blocked`；改动增强了指导，没有重新判定任务事实。

该新版任务文字从 2,126 字节增加到 4,467 字节；旧版为 7,157 字节。字节数不是 token 数，也不是效果评分。

额外将该任务（包含证据资源）与一个“剩余 100 步、单次上限 50 步”的资源结果组成交付包，测得：

| 形式 | 完整交付包 UTF-8 字节数 |
| --- | ---: |
| `json` | 2,876 |
| `text_json` | 8,459 |
| `text` | 9,000 |

该具体组合的两种带说明形式都会超过 8 KiB。调用方需要按自身输入和 tokenizer 核对预算、合理配置额度或自行编排 JSON；不能认为旧额度天然足够。这不是所有任务的固定大小或建议预算。预算超限仍返回 `context_budget_insufficient`，不会静默降级、裁剪或扩充限额。没有修改任何实际任务的预算、包版本绑定或安装环境。


## 后续更新：所有组件按任务类型适配

组件现在统一接收 `input.task.kind`，并在结果和有状态组件的历史中记录类型。各组件增加对应 execution、reasoning、hybrid 的用途建议；需要按类型改变实际计算时，通过 `request.task_variants` 明确选择输入字段或 focus。完整规则见 [任务类型使用说明](task-kind-usage.md)。

新增验证覆盖十个组件 × 三类任务 × 三种显示形式的内容与指导、组合传播、引用上游、错误来源范围、历史类型冲突和 CLI。适配器还检查全部 11 个适配器在未启用 task_context 时显式传递三种类型。最终完整离线测试为 79 项，以上 64 项是前一阶段结果。

类型元数据和建议增加后，同一任务示例的文字为 5,038 字节；同一任务与资源组合交付包为 JSON 3,286、文字加 JSON 9,651、纯文字 10,302 字节。这些是新增类型传播后的测量，取代上文用于当前预算估算的旧数字。预算仍由调用方设置，不会自动放宽。
